# AI-CRMS Database Schema Audit

## Scope
Audited the cumulative AI-CRMS database layer: `models.py`, `schemas.py`, `database.py`, `seed_data.py`, and all API routers. No destructive migration was introduced.

## Executive summary

The schema is structurally sound for the current academic prototype, but several integrity gaps were identified: SQLite foreign keys were not explicitly enabled; many domain values were unconstrained strings; the case/criminal association and evidence identifiers lacked database-level uniqueness; several persisted fields were missing from API create/output schemas; and case creation could commit a parent row before validating all child references.

## Problems found and changes

### 1. SQLite foreign-key enforcement
SQLite does not enforce declared foreign keys unless `PRAGMA foreign_keys=ON` is enabled for every connection. The database engine now installs a connection listener that enables this pragma.

### 2. Duplicate case/criminal links
Application code already attempted duplicate detection, but concurrent requests could still create duplicates. A database-level unique constraint on `(case_id, criminal_id)` was added.

### 3. Duplicate evidence numbers within a case
Evidence numbers are generated by the application and were not database-unique. A unique constraint on `(case_id, evidence_number)` was added.

### 4. FIR number uniqueness
FIR numbers are identifiers and should not be duplicated. A unique index was added; SQLite permits multiple NULL values, so legacy records without FIR numbers remain valid.

### 5. Domain enum consistency
Case status and prediction status already use SQLAlchemy/Pydantic enums. Threat level, case priority, evidence status, and victim status were plain strings. API schemas now validate their supported values while preserving the existing string-backed database columns for backward compatibility.

### 6. API/model field mismatch
`Criminal.fingerprint_id` existed in the model but was not accepted by `CriminalCreate`. `Evidence.chain_of_custody` and `Evidence.file_url` existed in the model but were not fully represented by the API schemas. These fields are now exposed where appropriate.

### 7. Case creation atomicity
Case creation previously committed the parent case before validating all criminal IDs. The workflow is now atomic: all criminal references are validated first, the case and links are flushed in one transaction, then committed. Duplicate criminal IDs are rejected.

### 8. Relationship deletion behavior
Case child relationships now use SQLAlchemy `delete-orphan` cascades so deleting a case does not leave orphaned case-criminal, evidence, victim, or prediction rows at the ORM layer. Criminal history and case-criminal rows likewise use delete-orphan from their parent relationship. This is intentional referential cleanup rather than a destructive migration of existing data.

## Timestamp assessment

The project consistently uses SQLAlchemy `DateTime(timezone=True)` with `func.now()` for created timestamps. SQLite stores datetime values without a native timezone type, so timezone semantics are application-managed. The project should continue treating API timestamps as UTC and should avoid mixing local wall-clock timestamps with persisted UTC values. Existing code still uses `datetime.utcnow()` in some generation/reporting paths; standardizing those call sites to timezone-aware UTC datetimes is a future cleanup, not required for this integrity patch.

## Migration strategy

There is no Alembic migration system in the current project. The existing application uses startup compatibility functions. This update follows that pattern with `ensure_integrity_indexes()`. It:

1. Checks whether required tables exist.
2. Detects duplicate legacy rows before creating unique indexes.
3. Refuses to silently weaken the constraint if duplicates are found.
4. Creates indexes without dropping or rewriting data.

If a future production deployment needs complex schema evolution, Alembic should replace ad-hoc startup migrations.

## Remaining recommendations

- Introduce Alembic before production deployment.
- Consider explicit SQLAlchemy enums/check constraints for all controlled string domains once a formal migration system exists.
- Add normalized/case-insensitive uniqueness policy for email addresses if the business rule requires email identity to be case-insensitive.
- Add retention/archival policy for audit and recovery tables.
- Add composite indexes only after observing production query plans.
